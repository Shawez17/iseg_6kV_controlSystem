# HV Control System Implementation Plan

## Project Context

Target hardware:
- WIZnet W5100S EVB Pico
- RP2040 MCU
- W5100 Ethernet module
- TFT display
- ADS1115 ADC channels
- GP8XXX DAC output module

The current firmware is a compact Arduino-style project. The next iteration should clean up the structure, standardize naming, add transport selection between USB and Ethernet, improve the command interface, and make the TFT a useful status and trend display.

Known GPIO pins from the current `config.h`:
- `I2C_SDA_PIN = 2`
- `I2C_SCL_PIN = 3`
- `LED_GPIO = 25`
- `TFT_CS = 13`
- `TFT_DC = 14`
- `TFT_RST = 15`

## Main Goals

1. Build a stable hardware layer for ADC, DAC, and shared runtime state.
2. Add a clean command transport layer for USB and Ethernet with GPIO-based selection.
3. Add a TFT user interface with startup, live status, and GPIO-selected trend mode.

## Proposed Code Structure

Keep the firmware modular and centered around a thin main file.

### Existing modules to keep

- `control-system.ino`
	- Bootstraps hardware.
	- Creates the global module instances.
	- Calls setup once and then runs the per-loop service functions.
- `config.h`
	- Board pins, constants, limits, timing, scaling factors.
	- Transport selection pin and network constants.
- `state.h`
	- Runtime measurements, setpoints, flags, transport state, and UI mode.
- `hardware_i2c.h/.cpp`
	- I2C bus setup.
	- ADC reads.
	- DAC writes.
- `display_ui.h/.cpp`
	- TFT init screen.
	- Live telemetry screen.
	- Trend screen rendering.
- `serial_commands.h/.cpp`
	- Command parsing.
	- Command dispatch.
	- Transport-agnostic read/write wrapper.

### New modules to add if needed

- `network_transport.h/.cpp`
	- W5100 TCP server setup.
	- Client accept/reconnect logic.
	- Read/write abstraction for Ethernet command input.
- `command_parser.h/.cpp`
	- Shared parser for USB and Ethernet input.
	- SCPI-like command decoding.
- `transport_mux.h/.cpp`
	- Selects active transport based on the GPIO input pin.
	- Switches between USB and Ethernet cleanly.
- `trend_buffer.h/.cpp`
	- Small ring buffers for recent voltage/current samples.
	- Optional if trend plotting is implemented in a dedicated helper.

## Naming and Cleanup Rules

Apply these rules consistently during the refactor:

- Use short but descriptive names.
- Prefer `camelCase` for functions and `snake_case` only if the existing style demands it.
- Use `k`-style or `constexpr` constants for fixed values.
- Avoid unscoped globals except for hardware drivers and shared runtime state.
- Keep all state that is updated in multiple modules in `SystemState` or a similar shared struct.
- Remove placeholder or duplicate names that do not convey behavior.
- Keep command names simple, direct, and consistent.

## Transport Design

The command interface should support two transports:

1. USB serial via `Serial`.
2. Ethernet TCP server via the W5100 module.

The active transport is selected by one GPIO pin:

- Pin high: Ethernet command transport enabled.
- Pin low: Ethernet command transport disabled, USB remains active.

Behavior expectations:

- USB remains active when Ethernet is enabled, but it must not accept voltage read/set commands while Ethernet mode is active.
- The firmware should prefer the enabled transport for command input.
- Ethernet should act as a simple TCP server with a fixed IP configuration.
- If the transport pin changes state, the system should re-evaluate the active command source on the next loop cycle.
- The command layer must reject voltage commands from the inactive transport, but still allow non-destructive status or debug queries if needed.
- Transport status should be visible to both the serial console and the TFT.

## Command Language

Use a SCPI-like style, but keep commands short enough for easy typing on serial terminals.

Suggested command groups:

- `SYST:DBG ON|OFF` or `DEBUG ON|OFF`
	- Toggle debug mode.

- `SOUR:VOLT <ch>, <value>`
	- Set requested voltage for a channel.

- `SOUR:DAC <ch>, <code>`
	- Set the raw DAC code for a channel.

- `MEAS:VOLT?`
	- Read measured voltages.

- `MEAS:CURR?`
	- Read measured currents.

- `CONF:IP <address>`
	- Set or report fixed IP configuration if supported over USB setup.

- `CONF:TRAN?`
	- Report active transport.

- `DISP:MODE <LIVE|TREND>`
	- Switch between live readout and trend display.

Implementation preference:

- Accept simple, unambiguous command strings.
- Normalize input by trimming whitespace and uppercasing the command token.
- Return a clear error message for malformed commands.
- Use voltage-based commands for normal operation.
- Keep raw DAC commands available for debug mode and low-level calibration.
- Voltage commands should convert from volts to DAC codes through the existing calibration/scaling path.
- Raw DAC commands should bypass voltage conversion and write the requested code directly.
- Readback commands should report both raw values and engineering units when practical.

## Display Design

The TFT should have three display states:

1. Startup screen
	 - Board name.
	 - Firmware name or version.
	 - Transport mode.
	 - ADC/DAC initialization status.
	 - Network status if Ethernet is enabled.
2. Live status screen
	 - Positive and negative channel voltage.
	 - Positive and negative current.
	 - DAC codes or setpoints.
	 - Debug flag and transport state.
3. Trend screen
	 - Small time-history plot for voltage and current.
	 - Separate traces for the two channels if practical.

Keep the startup screen brief and informative. The live screen should remain the default. The trend screen should be a separate mode that is switched by GPIO input, similar to the USB/Ethernet transport selector. The display should switch modes automatically when the selector changes.

## Implementation Phases

### Phase 1: ADC, DAC, and core hardware

Goal:
Build the low-level hardware foundation first and make the shared runtime state explicit.

Work items:
- Clean up the core hardware code and naming.
- Initialize and validate ADC hardware.
- Initialize and validate DAC hardware.
- Keep shared runtime values organized in `SystemState`.
- Add any missing runtime fields needed for transport mode, display mode, and command state.
- Preserve the DAC calibration/scaling path so voltage commands can map cleanly to DAC codes.
- Keep hardware setup in a thin and readable main flow.
- Keep the measurement update loop bounded so ADC and DAC servicing remain predictable.

Exit criteria:
- ADC and DAC modules initialize correctly.
- Core measurements and DAC outputs behave as expected.
- Shared state is complete enough for transport and display layers to consume.

### Phase 2: Serial communication and transport

Goal:
Add a transport layer for USB and Ethernet command handling, with GPIO-based mode selection.

Work items:
- Add the W5100 TCP server setup.
- Add the USB/Ethernet transport selector using GPIO input.
- Keep USB active while Ethernet is enabled, but block voltage query/set commands on USB in Ethernet mode.
- Create a shared command interface for both transports.
- Implement the SCPI-like parser for voltage commands, debug commands, and raw DAC debug commands.
- Add readback and error handling for malformed input.
- Define which commands are always allowed, which are transport-restricted, and which are debug-only.
- Make command responses consistent across USB and Ethernet.
- Support clear status reporting for transport, debug state, and current setpoints.

Exit criteria:
- Commands can arrive from either USB or Ethernet.
- The active transport is reported clearly.
- Voltage control follows the transport rules.
- The command parser cleanly separates normal voltage control from low-level DAC control.

### Phase 3: Display screen and tools

Goal:
Add the TFT user interface and supporting display tools, with automatic mode switching.

Work items:
- Add a startup/init screen.
- Show live voltages, currents, DAC state, and transport/debug status.
- Add a separate trend display mode.
- Make display mode switching automatic using GPIO input.
- Add lightweight trend plotting or history visualization.
- Keep the display update logic bounded so it does not block control timing.
- Make the startup screen show board identity, init results, and active transport/mode.
- Keep the live screen as the default operational view.
- Make the trend screen read-only and visually distinct from the live view.

Exit criteria:
- The display clearly shows boot status, live telemetry, and trend mode.
- Display switching happens automatically and does not disrupt the control loop.
- The display content matches the current transport and control state.

## Suggested Runtime Flow

1. Boot hardware.
2. Initialize config, ADC, DAC, display, and network transport.
3. Show the startup screen.
4. Enter the main loop.
5. Read the transport select pin.
6. Poll the active command transport.
7. Parse and dispatch commands.
8. Update ADC readings.
9. Update DAC outputs.
10. Refresh the display according to the current mode.

## Open Decisions Before Coding

These items should be confirmed before implementation starts:

- Exact GPIO pin for USB/Ethernet selection.
- Exact GPIO pin for trend mode selection.
- Fixed IP, subnet, gateway, and TCP port.
- Whether the Ethernet transport should be the only source allowed to query or set voltages while USB stays connected.
- Whether the SCPI voltage commands should map directly to DAC codes or convert volts to DAC codes through calibration.
- Whether trend plots should be available only in trend mode or also inside the live screen.

## Working Rule

Implement the plan in small steps. Keep each phase testable before moving to the next phase. Avoid broad refactors that are not needed for the currently selected phase.
